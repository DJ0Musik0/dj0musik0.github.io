FIELD//TONE is a proposed iPhone field-recorder for creators who capture sounds while traveling—train brakes, rain, footsteps, a market stall, a ferry horn—and turn them into short, licensed, intelligible Spotify-ready audio advertisements. A DJ-K0D3 engineering concept, not a released application.

00 / PROBLEM DEFINITION

A field recording shouldn't disappear into the camera roll.

Most phones can capture audio. Few workflows let a traveling producer go from location sound → tagged sample → non-destructive edit → voiceover → campaign export without bouncing between apps. FIELD//TONE narrows the task to an end-to-end 15-second creative, with a 30-second option.

A Halifax-to-Toronto trip becomes a sound palette: waterfront ambience, transit texture, street percussion and the click of a storefront door. No crowd recordings should be commercially reused without appropriate permissions; the app surfaces a rights checklist before export.

Key product constraint: We generate ad assets, not Spotify campaigns. Buying media, uploading final assets, choosing targeting and approvals occur in Spotify's advertising products. No undocumented Spotify ad-upload API is assumed.

See Spotify's current audio creative specifications: standard music ads are at most 30 seconds; supported files include MP3/WAV/OGG, at 44.1 kHz, stereo, 192–320 kbps where relevant, with a -16 LUFS ±1.5 LU target. Export should validate against the live spec, not hard-code an eternal contract.

Native first. Web later.

03 / IMPLEMENTATION NOTES / XCODE

Build the recording spine.

Start with an Xcode iOS app target, SwiftUI lifecycle, microphone usage description, and an actor/service to coordinate audio state. This trimmed Swift example illustrates the capture path rather than a complete production controller; real code needs interruption observers, file lifecycle handling, route-change recovery and tests.

import AVFoundation

final class FieldRecorder {
    private let engine = AVAudioEngine()
    private var file: AVAudioFile?

    func begin(url: URL) throws {
        let session = AVAudioSession.sharedInstance()
        try session.setCategory(.playAndRecord,
                                mode: .default,
                                options: [.defaultToSpeaker])
        try session.setActive(true)

        let input = engine.inputNode
        let format = input.outputFormat(forBus: 0)
        file = try AVAudioFile(forWriting: url,
                               settings: format.settings)
        input.installTap(onBus: 0,
                         bufferSize: 1024,
                         format: format) { [weak self] buffer, _ in
            try? self?.file?.write(from: buffer)
        }
        engine.prepare()
        try engine.start()
    }

    func stop() {
        engine.inputNode.removeTap(onBus: 0)
        engine.stop()
        file = nil
    }
}

// Request microphone permission before calling begin().
// Use a serial writer pipeline in production: never assume
// arbitrary file I/O inside a real-time audio callback is safe.

Engineering caveat: the tap above is intentionally minimal. For production, minimize work on audio callbacks; enqueue audio buffers into a bounded, allocation-aware writer queue and watch backpressure. Detect Bluetooth routes (and their different signal characteristics), interruptions, input format changes and disk exhaustion.

Failure-state checklist

  • Bluetooth call profile changes input bandwidth; present route status and record test clip.
  • OS interruption occurs mid-recording; finalize usable segments and show recovery state.
  • Very loud street sound clips the input; surface peak overload warnings, not only RMS.
  • Background ambience masks speech; duck music under narration and audition on phone speakers.
  • GPS metadata reveals sensitive travel; make geotagging manual/off by default and strip location from exported ads.
  • Recognizable voices or copyrighted music enter the clip; require human rights review, not automated approval.
04 / MVP / SCOPE FREEZE

Test the riskiest assumption.

The MVP question is not "can a phone record sound?" It is whether a creator can capture an original, usable ambient clip on a walk and finish a clear 15-second ad in one sitting. The ShoutEx MVP development guide provides the framework: one end-to-end user outcome before feature expansion.

SHIP

First release

Mic recording, clip naming, local library, trim, two-layer timeline, user-recorded narration, fade/gain, preview, offline render, QC summary and share-to-Files.

DEFER

Not yet

Cloud accounts, AI voice cloning, automatic location tracking, full multitrack DAW, template marketplace, automated Spotify ad deployment and payments.

MEASURE

Acceptance

Time to first usable capture, project completion rate, export failures, rights-review completion, offline success and repeat creation within seven days.

For prioritization after a pilot, consult ShoutEx's deeper question on turning app reviews and feedback into roadmap priorities. Cluster real complaints from creators; don't use AI to invent demand.

05 / RELEASE ENGINEERING + COMMUNITY

Launch with an actual listening party.

A small Halifax listening session provides a better first test than a large launch announcement. Invite producers, DJs, small-business owners and independent artists to arrive with one original sound from their day. Have everyone build a short spot, listen on speakers and submit structured feedback.

  1. T–21 days: internal TestFlight builds, privacy review and 5–10 capture sessions.
  2. T–14 days: invite a qualified local cohort; share the task and device requirements.
  3. T–7 days: run audio export verification on multiple iPhone routes; rehearse demonstrations.
  4. Launch evening: capture walk, 15-second production sprint, listening showcase, consent-cleared recordings only.
  5. T+2 days: collect completion rates, blockers and sample exports; triage by severity.

For targeted physical invitations, adapt the event planning and timing ideas in Yotru's pre-event direct-mail playbook. Its trade-show audience is different from this listening party, so use the invitation timing and specific call-to-action principles rather than assuming the same mailing volumes or outcomes.

Technical release gates: crash-free capture tests, no lost projects, permissions copy reviewed, TestFlight feedback channel, no user-sound telemetry by default, explicit rights checklist, reliable file exports. Avoid calling this a Spotify-integrated advertising tool until a real approved integration exists.
